## Redis(원격 딕셔너리 서버, Remote Dictionary Server)란?

> Key, Value 구조의 비정형 데이터를 저장하고 관리하기 위한 오픈 소스 기반의 NoSQL 키/값 저장소이다.

### Redis의 특징

- Key, Value 구조이기 때문에 쿼리를 사용하지 않아도 된다.
- 메모리에서 처리하는 구조이기 때문에 속도가 빠르다. but 설정에 따라 디스크 영속화를 지원한다.
- String, Lists, Sets, Sorted, Sets, Hashes 자료 구조를 지원한다.
- Single Threaded
  Redis는 명령 실행이 주로 single-threaded이다. 하지만 네트워크 I/O, persistence 등 일부 작업은 별도 스레드/프로세스를 사용할 수 있다.
- 다수의 언어를 지원함
- 디스크 영속화 : 데이터를 디스크에 저장할 수 있으며, 서버에 치명적 문제가 발생하더라도 디스크에 저장된 데이터를 통해 복구가 가능함

### Redis 사용에 주의할 점

- 서버에 장애가 생기거나 했을 경우, 그에 대한 운영 플랜이 꼭 필요하다.
  why?
  - 메모리를 사용하는 데이터베이스 특성상 서버에 장애가 생길 경우 데이터 유실이 발생하기 때문이다.
- 메모리 관리가 중요하다.
- 싱글 스레드의 특성상, 한 번에 하나의 명령만 처리할 수 있다. 처리하는데 시간이 오래 걸리는 요청, 명령은 피해야한다.

## 캐시 서버(Cache Server)에 대해서

데이터 베이스가 존재하나, **Redis** 같은 인메모리 데이터 구조 저장소를 별도로 사용하는 이유는 데이터 베이스는 데이터를 물리 디스크에 직접 쓰기 때문에 문제가 발생하여 다운되더라도 데이터가 손실되지 않는 장점이 있으나, 매번 디스크에 접근해야 하기 때문에 클라이언트가 많아질 수록 부하가 많아져 느려진다.

그렇기 때문에 사용자가 많지 않은 서비스의 경우, Web - WAS - DB 의 구조로도 무리가 가지 않지만, 클라이언트가 늘어남에 따라 과부하가 될 수 있기 때문에 이를 막기 위해 **캐시 서버**를 도입한다.

캐시는 한 번 읽어온 데이터를 임의 공간에 저장하여 다음에 읽을 때는 빠르게 값을 받을 수 있도록 도와준다. 같은 요청이 여러 번 들어오는 경우 매번 캐시 서버에 저장된 값을 바로 출력하기 때문에 DB의 부하를 줄이고 서비스의 속도를 챙길 수 있는 장점이 있다.

## 주요 활용 사례

- **캐싱**
  다른 데이터베이스 보다 앞에 배치된 Redis는 성능이 뛰어난 인메모리 캐시를 생성하여 엑세스 지연 시간을 줄여주고, 처리량을 늘리고, NoSQL 데이터베이스의 부담을 줄여준다.
- **세션 관리**
  Redis는 세션 관리 작업에 적합하다. Redis를 세션 키에 대한 적절한 TTL을 설정하여 Key-Value 스토어로 사용하면 간단하게 세션 정보를 관리할 수 있다.
- **실시간 순위표**
  Redis Sorted Set 데이터 구조를 사용하여 요소가 목록에 유지되고 점수에 따라 자동 정렬된다. 이를 통해 비교적 쉽게 동적 순위표를 구현할 수 있으며 순위표 뿐만 아니라 좋아요가 가장 많은 정렬순이나 선두에 있는 사람이 누구인지 보여주는 다양한 사례에 적용이 가능하다.
- **채팅 및 메세지**
  Redis는 PUB/SUB 표준을 지원한다. 따라서 고성능 채팅방, 실시간 코멘트 스트림 및 서버 상호 통신을 구현할 수 있다.
  여기서 PUB/SUB 표준이란?
  > Publisher가 메세지를 토픽에 발행하면, 해당 토픽을 Subscriber한 수신자들에게 메세지를 전달하는 비동기 메세지 패턴이다.

## OCR 관련 프로젝트에 어떤 방식으로 사용하였는지?

업로드 한 자료에서 개인정보를 OCR로 인식해서 마스킹 해주는 프로젝트에서 Redis를 캐시가 아니라 OCR 작업 큐로 사용했다.

흐름은 다음과 같다.

```
  사용자가 문서 업로드
  -> 백엔드는 문서 정보를 DB에 저장
  -> Redis에 "이 문서 OCR 처리해줘" 작업 등록
  -> worker가 Redis에서 작업을 가져감
  -> OCR 처리
  -> 결과를 DB에 저장
  -> 문서 상태를 Completed 또는 Failed로 변경
```

Redis로 구현한 이유는 **OCR이 오래 걸리는 작업이기 때문이다.**

만약 Redis를 사용하지 않는다면

```
  사용자 업로드 요청
  -> 파일 저장
  -> OCR API 호출
  -> 개인정보 탐지
  -> 마스킹
  -> DB 저장
  -> 응답
```

위 과정처럼 되는데, 문제는 OCR이 이미지/PDF 처리 시간, Google Vision 외부 API 응답 지연 등 느릴 수 있다는 것이다.

그래서 프로젝트에서 업로드 API를 Redis를 사용하는 방식으로 바꾸었다.

```
  사용자 업로드 요청
  -> 파일 저장
  -> DB에 문서 상태 Queued 저장
  -> Redis에 OCR 작업 등록
  -> 사용자에게 바로 응답

  worker
  -> Redis에서 작업 가져옴
  -> OCR 처리
  -> DB에 결과 저장
```

여기서 **Redis는 API 서버와 OCR Worker 사이의 작업 전달소** 역할을 한다. 또한 단순 전달소 역할만 수행하는 것이 아니라 장애 대응 시스템으로도 활용했다.

단순 List 큐로 구현한다면 worker가 작업을 꺼낸 후 죽으면 그 작업은 사라질 수 있다. 그래서 Redis의 Streams + Consumer Group 기능을 사용하였다.

이걸 쓰면 “누가 어떤 작업을 가져갔는지, 아직 완료 확인을 안했는지”를 기억할 수 있다.

```
API -> XADD로 작업 등록
  Worker -> XREADGROUP으로 작업 읽기
  처리 성공 -> XACK으로 완료 확인
  worker 장애 -> pending 상태로 남음
  다른 worker -> 오래된 pending 작업을 회수해 재처리
```

즉 이 프로젝트에서 Redis를 도입한 이유는 4가지이다.

1. 업로드 응답을 빠르게 하기 위해
   - OCR을 기다리지 않고 “접수 완료” 바로 반환
2. OCR 작업을 백그라운드에서 처리하기 위해
   - API 서버와 OCR worker 역할 분리
3. worker를 여러 개로 늘려 처리량을 늘리기 위해
   - 실제 측정 결과 worker 3개에서 처리량 약 2.98배 증가
4. 작업 실패와 장애를 추적하고 복구하기 위해
   - ACK(작업 완료 확인), pending(가져갔으나 아직 완료 확인되지 않은 작업), recovery(ACK 전에 죽어 pending에 남은 작업을 다른 worker가 회수해 재처리하는 것), retry(실패한 작업 재시도), DLQ(계속 실패한 작업을 따로 모아두는 큐) 구현

### 정리

Redis의 장점은 빠르다는 것이지만 이 프로젝트에서 Redis를 쓴 이유는 “속도가 빨라서”가 아니다.

이 프로젝트에서 더 중요한 이유는 **OCR 작업을 안정적으로 비동기 처리하고 worker를 확장하기 위해서**이다.

1. 업로드 API와 OCR 처리 분리
   - 사용자가 문서를 업로드하면 API는 파일/DB 저장 후 바로 응답
   - 오래 걸리는 OCR은 worker가 백그라운드에서 처리
2. 작업 큐 역할
   - document_id를 Redis Stream에 넣고 worker가 가져가서 OCR 처리
3. 작업 신뢰성
   - ACK, pending recovery, retry, DLQ, document lock
4. 큐 상태 관측
   - 대기 작업 수
   - pending 작업 수
   - DLQ 수
   - consumer 상태

Redis의 빠른 처리 속도도 장점이지만, 이 프로젝트에서 Redis를 도입한 핵심은 **OCR 작업을 API 요청과 분리**하고 **안정적으로 비동기 처리**를 진행하기 위해서이다.

**Redis Streams consumer group**을 사용해 **worker scale-out**, **ACK 기반 완료 처리**, **pending recovery**, **retry**, **DLQ**, **document lock**을 구현했고, 큐 상태를 대시보드에서 관측할 수 있게 했다.

이를 통해 worker 3개 sclae-out 시 **처리량이 크게 증가**하고, **queue wait 크게 낮아**졌다.
